# 🗺️ From Maven to .NET: The Rosetta Stone

If you understand Maven lifecycle, dependency management, and multi-module builds, you already know 90% of .NET's build ecosystem. This guide maps your existing Java knowledge directly to .NET concepts using the .NET CLI and modern MSBuild practices.

---

## 🏛️ Core Architectural Mapping

| Java / Maven Concept           | Description                                                                          | .NET Equivalent                                  |
| :----------------------------- | :----------------------------------------------------------------------------------- | :----------------------------------------------- |
| **Artifact** (JAR / WAR)       | The compiled output containing executable code or libraries.                         | **Assembly** (DLL)                               |
| **`pom.xml` (Module)**         | The XML file defining a single project's dependencies and build settings.            | **`.csproj` (Project)**                          |
| **`pom.xml` (Parent)**         | A file used to pass down shared properties/compiler settings via folder inheritance. | **`Directory.Build.props`**                      |
| **Maven Dependency**           | The packaging and distribution format for external libraries.                        | **NuGet Package**                                |
| **Central Repository**         | The primary public repository for hosting and downloading packages.                  | **NuGet.org**                                    |
| **Local Repository** (`~/.m2`) | The local machine cache where downloaded packages are stored.                        | **Global Packages Folder** (`~/.nuget/packages`) |

---

## 🔄 Project Structures: Side-by-Side

### 🍃 Maven Multi-Module Layout

```text
my-app/
├── pom.xml (Parent: lists <modules> & <dependencyManagement>)
├── core-module/
│   └── pom.xml (Child: inherits parent)
└── web-module/
    └── pom.xml (Child: inherits parent)
```

### 🔷 .NET Multi-Project Layout

```text
MyApp/
├── MyApp.sln (Solution file: structural visual grouping)
├── Directory.Packages.props (Central version management)
├── src/
│   ├── MyApp.Core/
│   │   └── MyApp.Core.csproj (Independent project)
│   └── MyApp.Web/
│       └── MyApp.Web.csproj (Independent project)
```

> [!IMPORTANT] The Hierarchy Difference
> **Maven is bottom-up (Two-Way):** The parent lists modules, and children must explicitly declare a `<parent>` block.
> **.NET is top-down (Folder Inheritance):** Projects **never** point back up to a parent. Instead, files named `Directory.Build.props` and `Directory.Packages.props` automatically inject settings downwards into any `.csproj` file located in their subfolders.

## 🛠️ Dependency Management vs. Central Package Management (CPM)

In .NET, managing versions across a multi-project setup is called **Central Package Management (CPM)**. It uses a single file named `Directory.Packages.props` at your solution root.

### 1. The Version Dictionary

How to define a version blueprint without installing it yet.

```xml
<!-- 🍃 Maven: Parent pom.xml -->
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.fasterxml.jackson.core</groupId>
            <artifactId>jackson-databind</artifactId>
            <version>2.15.2</version>
        </dependency>
    </dependencies>
</dependencyManagement>
```

```xml
<!-- 🔷 .NET: Directory.Packages.props -->
<Project>
  <PropertyGroup>
    <!-- You MUST explicitly turn this switch on -->
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
  </PropertyGroup>
  <ItemGroup>
    <PackageVersion Include="Newtonsoft.Json" Version="13.0.3" />
  </ItemGroup>
</Project>
```

### 2. Consuming the Dependency

How a specific project opts-in to using that library.

```xml
<!-- 🍃 Maven: child-module/pom.xml -->
<dependencies>
    <dependency>
        <groupId>com.fasterxml.jackson.core</groupId>
        <artifactId>jackson-databind</artifactId>
        <!-- Version is omitted; inherited from management -->
    </dependency>
</dependencies>
```

```xml
<!-- 🔷 .NET: src/MyApp.Web/MyApp.Web.csproj -->
<Project Sdk="Microsoft.NET.Sdk.Web">
  <ItemGroup>
    <!-- Version is omitted; inherited from props file -->
    <PackageReference Include="Newtonsoft.Json" />
  </ItemGroup>
</Project>
```

> [!WARNING] Version Drift Enforcement
> Once `<ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>` is enabled, if a developer tries to hardcode a version inside a `.csproj` file (e.g., `<PackageReference Include="Newtonsoft.Json" Version="12.0.1" />`), the compiler will immediately throw a **Build Error (NU1008)**.

### 3. Forcing Global Dependencies

How to automatically force an entire repository to install a specific utility (like Lombok or a Code Linter).

```xml
<!-- 🍃 Maven: Parent pom.xml (Outside management) -->
<dependencies>
    <dependency>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
        <version>1.18.30</version>
    </dependency>
</dependencies>
```

```xml
<!-- 🔷 .NET: Directory.Packages.props -->
<Project>
  <ItemGroup>
    <!-- Automatically injects this into EVERY .csproj down the tree -->
    <GlobalPackageReference Include="SonarAnalyzer.CSharp" Version="9.32.0.97167" />
  </ItemGroup>
</Project>
```

## 🏃‍♂️ CLI Command Translation Guide

The `.NET CLI` acts exactly like the `mvn` command-line engine.

| Maven Command | .NET CLI Command | What it does |
| :--- | :--- | :--- |
| `mvn clean` | `dotnet clean` | Deletes the build outputs (`bin/` and `obj/` folders). |
| `mvn compile` | `dotnet build --no-restore` | Compiles code without pulling new packages. |
| `mvn test` | `dotnet test` | Executes unit tests via runners like xUnit or NUnit. |
| `mvn package` | `dotnet pack` | Bundles your compiled code into a reusable `.nupkg` package file. |
| `mvn install` | _No direct equivalent_ | .NET copies directly to output paths; global deployment uses local NuGet sources. |
| `mvn deploy` | `dotnet nuget push` | Uploads your packaged artifact to a remote feed (like NuGet.org). |
| `mvn architecture:generate` | `dotnet new <template>` | Scaffolds a new project from an archetypal template. |

> [!TIP] Automated Restores
> In Maven, running `mvn compile` automatically resolves dependencies. In older .NET versions, you had to run `dotnet restore` manually. In modern .NET, running **`dotnet build` or `dotnet run` automatically executes a restore** in the background for you.

## 🧩 Scope Mapping: Java Scopes vs .NET Properties

Maven defines _when_ a dependency is visible via `<scope>`. .NET handles this via XML attributes inside the `<PackageReference>` tag.

- **`compile` (Default)** $\rightarrow$ Standard .NET behavior. The dependency is available everywhere and flows transitively to downstream projects.
- **`provided` (e.g., Lombok)** $\rightarrow$ In .NET, use `PrivateAssets="all"`. This tells the compiler: _"Use this package to build this project, but do not pass it down to other projects that reference me."_
- **`test`** $\rightarrow$ .NET doesn't have a strict test scope attribute. Instead, you isolate your test frameworks completely inside your dedicated test projects (`.csproj`) so production apps never see them.

# Directory.Build.props vs. Directory.Packages.props

While both files use the same underlying MSBuild XML syntax and work via **folder inheritance** (automatically applying to any project in subdirectories), they serve entirely separate responsibilities in a .NET architecture.

## ⚡ Direct Comparison Overview

| Feature | 📁 `Directory.Build.props` | 📦 `Directory.Packages.props` |
| :--- | :--- | :--- |
| **Primary Purpose** | Global compilation settings and project metadata. | Centralized NuGet package version management (CPM). |
| **Maven Equivalent** | Parent POM properties and plugin configurations. | Parent POM `<dependencyManagement>` dictionary block. |
| **Typical Tags** | `<TargetFramework>`, `<Nullable>`, `<Version>`, `<Authors>` | `<ManagePackageVersionsCentrally>`, `<PackageVersion>`, `<GlobalPackageReference>` |
| **Execution Order** | Evaluated **first**, before the `.csproj` file is parsed. | Evaluated **implicitly** when package references are resolved. |

## 🔍 Deep Dive Breakdown

### 1. `Directory.Build.props` (The Global Settings Layer)

This file is used to enforce **compiler behaviors, code quality standards, and shared metadata** across every single project so you do not have to copy-paste common properties into individual `.csproj` files.

```xml
<!-- Directory.Build.props -->
<Project>
  <PropertyGroup>
    <!-- Force every project to target the same framework -->
    <TargetFramework>net9.0</TargetFramework>
    
    <!-- Enforce modern C# safety features universally -->
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    
    <!-- Treat all warnings as compilation errors (strict quality) -->
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    
    <!-- Shared NuGet package metadata for when you run 'dotnet pack' -->
    <Version>1.0.0-preview2</Version>
    <Authors>Enterprise Core Architecture Team</Authors>
  </PropertyGroup>
</Project>
```

### 2. `Directory.Packages.props` (The Version Registry Layer)

This file is strictly dedicated to **dependency version control**. Its sole job is to act as the central ledger for your NuGet external dependencies, keeping your local `.csproj` files clean and versionless.

```xml
<!-- Directory.Packages.props -->
<Project>
  <PropertyGroup>
    <!-- The master switch that turns on Central Package Management -->
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
  </PropertyGroup>

  <!-- The Version Dictionary (Just like <dependencyManagement>) -->
  <ItemGroup>
    <PackageVersion Include="Microsoft.EntityFrameworkCore" Version="9.0.0" />
    <PackageVersion Include="Newtonsoft.Json" Version="13.0.3" />
  </ItemGroup>

  <!-- Force-injected packages (Just like parent <dependencies>) -->
  <ItemGroup>
    <GlobalPackageReference Include="SonarAnalyzer.CSharp" Version="9.32.0.97167" />
  </ItemGroup>
</Project>
```

## 🏁 Summary Workflow: How They Interact Together

When you run `dotnet build` inside your **Codespaces workspace**, the .NET engine merges these files together behind the scenes in this order:

1. It searches up the folder tree and imports **`Directory.Build.props`** to set the base compiler settings (e.g., target `.NET 9` and treat warnings as errors).
2. It reads your individual project file (**`.csproj`**) to see which local features are enabled and which third-party packages are requested (e.g., `<PackageReference Include="Newtonsoft.Json" />`).
3. It references **`Directory.Packages.props`** to look up the exact version tag (`13.0.3`) for that requested package and force-injects any global analyzers.
