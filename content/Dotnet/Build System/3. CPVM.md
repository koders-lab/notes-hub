# 📦 Centralized NuGet Package Management (CPVM)

In modern .NET (v7+), package versions are managed centrally across a solution using **Central Package Management (CPM)**. This eliminates the need to update NuGet versions inside individual `.csproj` files, functioning exactly like a Maven `<dependencyManagement>` block.

---

## 🛠️ Setup Central Package Management

To enable CPM, you create a configuration file at the root of your solution alongside your `.sln` file.

### 1. Create the Directory.Packages.props File

Create a file named `Directory.Packages.props` in your root solution folder and paste this structure:

```xml
<Project>
  <PropertyGroup>
    <!-- Enable Central Package Management -->
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
  </PropertyGroup>

  <ItemGroup>
    <!-- Define your centralized package versions here -->
    <PackageVersion Include="Microsoft.EntityFrameworkCore" Version="9.0.0" />
    <PackageVersion Include="Newtonsoft.Json" Version="13.0.3" />
    <PackageVersion Include="xunit" Version="2.9.2" />
  </ItemGroup>
</Project>
```

### 2. Reference Packages in Your Projects (`.csproj`)

Inside your individual project files (e.g., `src/MyWebApi/MyWebApi.csproj`), you reference the packages **without** specifying a version attribute:

```xml
<Project Sdk="Microsoft.NET.Sdk.Web">
  <PropertyGroup>
    <TargetFramework>net9.0</TargetFramework>
  </PropertyGroup>

  <ItemGroup>
    <!-- Version is inherited automatically from Directory.Packages.props -->
    <PackageReference Include="Microsoft.EntityFrameworkCore" />
    <PackageReference Include="Newtonsoft.Json" />
  </ItemGroup>
</Project>
```

# Q.  Is similar to defining version of a jar in dependency managment, and sub modules using that version w/o explicit addition of it ?

Just like Maven's `<dependencyManagement>` acts as a single source of truth for your JAR versions, `.NET`'s `Directory.Packages.props` does the exact same thing for your NuGet package versions. \[1]

Here is the exact mapping of how the two workflows mirror each other:

## 1. Defining the Version (The Blueprint)

- In Maven: You define the version inside the parent `pom.xml` under `<dependencyManagement>`. The JAR is not downloaded or injected yet; you are just declaring _"If anyone asks for this artifact, use this version."_ \[2, 3, 4, 5, 6]
- In .NET: You define the version inside `Directory.Packages.props` using `<PackageVersion>`. Just like Maven, this does not actually install the package; it just reserves the version string for the solution. \[7, 8, 9, 10]

## 2. Using the Version (The Consumer)

- In Maven: The submodule adds the dependency under `<dependencies>` but leaves out the `<version>` tag. It inherits the version automatically from the parent.
- In .NET: The project file (`.csproj`) adds the dependency using `<PackageReference>` but leaves out the `Version="..."` attribute. It inherits the version automatically from the folder hierarchy. \[11, 12, 13, 14, 15]

## The One Big Advantage .NET Has Here

In Maven, a submodule must explicitly link to the parent using the `<parent>` tag, or it won't see the dependency management block.

In .NET, `Directory.Packages.props` works via folder inheritance. Any project file located in the folders below that file automatically picks up the versions. You don't have to write a single line of code in the child project to link it to the central version controller. \[16]

## ⚖️ Centralized Versioning: .NET vs. Maven

| Feature         | 🍃 Maven (`<dependencyManagement>`)                      | 🔷 .NET (Central Package Management)                                        |
| :-------------- | :------------------------------------------------------- | :-------------------------------------------------------------------------- |
| **File Name**   | `pom.xml` (Parent/Root)                                  | `Directory.Packages.props`                                                  |
| **Inheritance** | **Explicit**: Child must declare parent coordinates.     | **Implicit**: Any project folder below this file automatically inherits it. |
| **Tag Name**    | `<dependency><groupId>...<version>...</dependency>`      | `<PackageVersion Include="..." Version="..." />`                            |
| **Override**    | Allowed by defining `<version>` explicitly in the child. | Allowed via `<PackageReference Version="..." OverrideVersion="..." />`      |

## 💻 CLI Commands for Central Management

Use these commands to interact with packages when CPM is enabled:

- `dotnet add package <NAME>` — Adds the package reference to your `.csproj` and automatically appends the latest version to `Directory.Packages.props`.
- `dotnet list package` — Lists all packages used across the solution.
- `dotnet list package --outdated` — Checks for newer versions of packages across all projects.
